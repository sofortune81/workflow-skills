# Plan lifecycle

One format for every repo and every tool: where the file lives, what the ledger says, who
writes it, and when.

## Folders

The plan file moves as its status changes, so `ls` answers "what is active" without opening
anything.

| Folder | Holds | Plan status |
|---|---|---|
| `docs/plans/` | idle queue — nobody is on it | `PLANNED`, `PARKED` |
| `docs/plans/WIP/` | someone is on it | `IN PROGRESS`, `BLOCKED` |
| `docs/plans/completed/` | closed, nothing more happens | `COMPLETE`, `DROPPED` |
| `docs/plans/WIP/` with holder `owner` | waiting on the human owner, not on an agent | `IN PROGRESS`, `BLOCKED` |

`docs/plans/STATUS.md` is generated by `scripts/plan-status.js` on every commit and merge;
never edit it by hand, and **never commit it — it is gitignored**. It is per-checkout
derived state: two worktrees on different branches hold different plan files, so no two
copies can agree, and tracking it makes every merge resolve a generated file. It scans
**every** worktree, so one copy still answers "what is in flight anywhere" — the `Where`
column names the worktree a row was read from. When copies of one plan disagree, the live
one is the copy from the worktree its `holder:` names, or the main worktree's copy when the
holder is `owner` or absent; only what neither rule settles is listed under "Needs
attention". Run the script any time to refresh it.

Only `WIP/` and `completed/` are lifecycle folders. Any other subdirectory is an asset
directory and takes no part in the scheme.

Move with `git mv`, **in the same commit as the status-line change that caused it** — two
records of one fact drift the moment they are written apart.

```bash
mkdir -p docs/plans/WIP && git mv docs/plans/<plan>.md docs/plans/WIP/<plan>.md
```

Opening a run is the first commit; closing it into `completed/` is the last. A run that ends
unfinished does not move: it stays in `WIP/` as `IN PROGRESS` or `BLOCKED`, or returns to the
base directory as `PARKED` if nobody will pick it up soon.

## The ledger

**The ledger table is the only status record.** No prose "shipped" or "✅ done" elsewhere in
the plan, no per-task state in a session summary or a memory file. It sits above the preamble
so `sed -n '1,30p'` reads the whole run's state, and so slicing the preamble into subagent
briefs does not drag status into every brief.

````markdown
**Plan status:** IN PROGRESS · 1/4 done · branch `main` · holder: worktree `my-branch` · updated YYYY-MM-DD
**Resume at:** Task 2

## Ledger

| # | Task | Status | Commit | Evidence |
|---|---|---|---|---|
| 1 | Route bar | DONE | e59ec424 | vitest adminSections 6/6 |
| 2 | Rail module | REVIEW | 1a2b3c4d | — |
| 3 | Data states | BLOCKED | — | spec conflict, owner call |
| 4 | Save scope | TODO | — | — |
````

Plan status: `PLANNED` · `IN PROGRESS` · `BLOCKED` · `COMPLETE` · `PARKED` · `DROPPED`.

Preamble fields, in order: plan status · `N/M done` · `branch \`x\`` · `holder: …` · `updated
YYYY-MM-DD`.

- **`holder:` is mandatory when plan status is `IN PROGRESS` or `BLOCKED`.** It is either
  ``worktree `<dir name>` `` — the worktree directory the session works in, not the branch —
  or `owner`, meaning it is on the human owner and no agent is on it.
- **A second line `**Waiting on:** owner — <what>` is mandatory when plan status is
  `BLOCKED`**, naming who owes what. It sits directly under the status line, above
  `**Resume at:**`.

Task status — exactly these six, no synonyms:

| Status | Means |
|---|---|
| `TODO` | not dispatched |
| `WIP` | dispatched, in flight |
| `REVIEW` | code landed, verification not passed yet |
| `DONE` | verified and reviewed — Commit and Evidence both filled |
| `BLOCKED` | needs a decision or dependency — reason in Evidence, mandatory |
| `DROPPED` | descoped — reason in Evidence, mandatory |

## Rules

- **Commit the plan file as soon as it's written**, before any implementation starts — its
  own commit, not batched with the first task's code. An uncommitted plan in `docs/plans/`
  is invisible to `git log` and other tools, and can be lost with the rest of an uncommitted
  tree.
- **A plan is committed from wherever it was written — the primary checkout and the trunk
  included.** The worktree usually does not exist yet: cutting it is the first thing the
  plan tells the executor to do. A repo whose pre-commit hook refuses commits in the
  primary checkout must therefore exempt a commit whose staged paths are ALL under
  `docs/plans/`, and refuse as before the moment one code file joins them. `OWNER_COMMIT=1`
  is not the answer — it also disables the ledger gate, on the one commit that introduces a
  ledger. In this setup the exemption is gate 1 of `.githooks/pre-commit`.
- **Seed the ledger when the plan is written**, one row per `### Task N`, every row `TODO`.
  A row added mid-run cannot be told from a task nobody planned, and the row count at write
  time is the scope contract.
- **Whoever holds the plan is its only writer.** Subagents never edit the plan file —
  parallel implementers collide on the same rows, and the sub's report is what the row is
  written from.
- **The row is committed per task, never batched at the end.** It rides the task's code
  commit as `REVIEW`, then flips to `DONE` in a ledger-only commit straight after, naming
  the code commit's sha. A commit cannot carry its own sha, and amending to insert one mints
  a new sha. Each task's pair of commits is its own proof, and a missed flip shows as a
  dirty plan file.
- **`REVIEW` and `DONE` are different claims.** `DONE` needs an Evidence cell holding a real
  output line (`vitest 6/6`) — never "tests pass". "It compiles" is not verification, and a
  wrapper's summary line is not evidence; run the command unfiltered.
- **`WIP` never survives a session.** Resolve every WIP row before finishing. Unfinished is
  fine and is recorded as `TODO` or `BLOCKED` with a reason.
- **Every task carries a `Verify:` line** naming the exact command. It is what earns `DONE`;
  without it the `REVIEW → DONE` transition is unfalsifiable.

## Setting up a repo

A repo without this structure gets it before its first plan is written, so every project
looks the same and non-Claude tools have something in-repo to read:

```bash
node ~/.kimi-code/skills/plan-lifecycle/scripts/init-plans.js --dry
```

Then again without `--dry`. It is idempotent: it creates the three folders, writes
`docs/plans/README.md` from this skill's template, adds a pointer row to whichever agent
entry files the repo has (`CLAUDE.md`, `AGENTS.md`, `.trae/rules/CLAUDE.md`), and syncs any
vendored skill copies. `--force` also rewrites a README that has drifted.

It never moves, edits, or reads a plan file. Existing plans are left exactly as they are.

**Edit `templates/plans-README.md` in this skill, never a rendered copy**, then re-run the
script in each repo.

## Enforcement

A Claude Code Stop hook (`~/.kimi-code/hooks/plan-ledger-gate.js`) refuses to let a session end
while a plan contradicts the rules above: a row still `WIP`, a `DONE` row with no Commit or
Evidence, a `BLOCKED`/`DROPPED` row with no reason, a status word outside the six, or a file
in the wrong folder for its status. It only reports — it prints the exact `git mv` and never
touches a file itself.

The hook is Claude-only. Other tools follow the same rules through the repo's
`docs/plans/README.md`, which is why that file has to exist in every project.
